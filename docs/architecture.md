# 設計・構成ドキュメント（akiba-ueno-card-map-demo）

最終確認: 2026-11-25（対象コミット: main `167e260`）
この文書は、現行デモの構成を「何が・どこに・どう連携するか」で固定し、今後の変更で迷わないための正本とする。実態と食い違う変更をしたら、この文書も同じ PR で更新する。

## 1. 概要と前提

- 目的: 秋葉原〜上野エリアの架空カードショップ 9 店舗を、検索・絞り込み・略図／実地図ピン・詳細表示で探せることを示す静的デモ。実店舗案内ではない（README と画面内の注意書きが前提）。
- 形態: ビルド不要の静的サイト。フレームワーク、バンドラ、パッケージ管理（package.json）は使わない。`dist/` をそのまま HTTP サーバーで配信するだけで動く。
- 外部依存は実行時のみ 2 系統に限定する:
  - 地図タイル／地図ライブラリ: 国土地理院タイル（淡色地図）と MapLibre GL JS 5.6.1（unpkg CDN）。読み込み失敗時は同梱の SVG 略図＋ピンのフォールバックで全機能が使える。
  - Google マップ: 埋め込みではなく外部リンク（位置表示・徒歩ルート）のみ。API キーは使わない。
- 位置情報は取得しない。保存は利用者本人のブラウザ内（localStorage）のみで、サーバー送信は行わない。

## 2. 画面構成

単一ページ（`dist/index.html`）に 2 画面を持ち、`location.hash` で切り替える SPA 的構成。画面遷移でページ再読み込みはしない。

### 2.1 店舗検索画面（`#map-view`、初期表示）

| 領域 | 要素 | 役割 |
| --- | --- | --- |
| ヘッダー | `.mast` | ブランド表示と画面切替ナビ（店舗検索／店舗管理、`aria-current` で現在画面を示す） |
| 導入 | `.intro` | タイトル、説明、「架空データ・非公式デモ」の注意 |
| 検索ツール | `.tools` 内 `#search` | 検索方法の切替（地名・駅名／店名）、キーワード入力、リセット。店舗タイプのラジオ絞り込み（すべて／shop／play／retail） |
| 店舗一覧 | `#results`（`#list`, `#count`, `#empty`） | 絞り込み結果をボタン行で列挙。0 件時は空状態とリセットボタンを表示 |
| 地図 | `.map-pane`（`#mapbox`, `#tiles`, `#schematic`, `#fallback-pins`） | 駅ボタン（秋葉原／御徒町／上野）で絞り込み。実地図が有効になるまでは SVG 略図にピンを重ねる |
| 詳細 | `#detail` | 選択店舗の名称・駅・エリア・種別と Google マップ外部リンク 2 本。未選択時は案内文 |
| 同位置グループ | `#pin-group` | 同一座標に複数店舗がある場合の選択パネル |
| フッター | `footer` | 注意書きと初期データ CSV（`stores.csv`）のダウンロードリンク |

選択状態は URL ハッシュ `#shop=<id>` にも反映し、リンク共有・再読み込みで復元できる（管理画面表示中は上書きしない）。

| 領域 | 要素 | 役割 |
| --- | --- | --- |
| 登録一覧 | `#cms-list`, `#cms-count` | 登録済み店舗の一覧と「編集」ボタン |
| 編集フォーム | `#cms-form` | 店舗名・最寄り駅・エリア・店舗タイプ・緯度・経度（全て必須）。追加／更新／削除、新規入力へのリセット |

## 3. データモデル

### 3.1 店舗レコード（Store）

正本の定義は `dist/store-data.js` の `StoreData.validate()`。全ての入力経路（初期 JSON、localStorage、管理画面フォーム、インポート JSON）は必ずこの検証を通る。

| フィールド | 型 | 制約 |
| --- | --- | --- |
| `id` | string | `^[0-9]{2,4}$`、一覧内で一意。新規採番は `nextId()` が未使用の最小番号を 2 桁ゼロ埋めで返す |
| `name` | string | 前後空白を除去して 1〜80 文字 |
| `station` | string | `秋葉原`／`御徒町`／`上野` のいずれか |
| `area` | string | 前後空白を除去して 1〜80 文字 |
| `type` | string | `shop`（カードショップ）／`play`（対戦スペース）／`retail`（取扱店）。表示名は `StoreData.labels` |
| `lat` | number | 35.6968〜35.7164（`StoreData.region` の南端〜北端） |
| `lon` | number | 139.7652〜139.7818（同、西端〜東端） |

- 一覧の制約: 配列であること、250 件以下、ID 重複なし（`validateRows()`）。
- 地図範囲: `region = [[139.7652, 35.6968], [139.7818, 35.7164]]`（南西〜北東）。地図の表示範囲・ピン換算・座標検証が共通で使う。

### 3.2 データの置き場所と更新方法

| データ | 置き場所 | 正本／生成 | 更新方法 |
| --- | --- | --- | --- |
| 初期店舗データ | `dist/stores.csv` | 正本（人手編集用） | CSV を編集し `node build-data.mjs` で検証＋再生成 |
| 初期店舗データ（配信形） | `dist/stores.json` | 生成物（手編集しない） | `build-data.mjs` が CSV から生成。ヘッダー、ID 形式（2 桁）、駅・種別、座標の広域範囲（lon 139.76〜139.79、lat 35.69〜35.72）を検証する |
| 利用者の編集データ | ブラウザ localStorage、キー `card-map-demo-stores-v1` | 端末ローカルのみ | 管理画面の追加・編集・削除・インポートで更新。形式は `{version: 1, stores: [...]}`（`StoreData.encode()`／`parse()`） |
| バックアップ | 利用者が保存する JSON ファイル | 持ち出し用 | 管理画面「JSONを保存」で書き出し、「JSONを読み込む」で復元 |

読み込み優先順位（`app.js` の `boot()`）:

1. localStorage に保存済みデータがあれば、それを検証して使う。
2. 保存が無い／読めない場合は `stores.json` を fetch して検証し、初期データとして表示する（読めなかった場合はその旨を画面に表示し、初期データを表示する）。
3. どちらも失敗したら「読み込めませんでした」を表示し、管理画面も初期化失敗として扱う。

保存時の競合対策（`cms.js` の `profileSave()`）: 保存前に localStorage の現在値が「編集開始時点で読んだ値」と一致するかを確認し、別タブで更新されていたら保存を中止して再読み込みを促す。

検証範囲の差に注意: `build-data.mjs`（CSV 側）は ID 2 桁固定・座標は広域範囲と、実行時検証（ID 2〜4 桁・`region` 範囲）より緩い部分と厳しい部分が混在する。CSV に載せる初期データは、両方の検証を通る値にすること（現行 9 件は両方を満たす）。

## 4. コンポーネント分割（現行）

ビルド単位ではなく、責務単位でファイルが分かれている。読み込み順は `index.html` の `defer` 順（store-data → app → cms）で固定する。

| ファイル | 責務 | 依存 |
| --- | --- | --- |
| `dist/index.html` | 画面骨格、略図 SVG、フォーム定義、スクリプト／CSS の読み込み順 | なし |
| `dist/style.css` | 全画面のスタイル | HTML のクラス／ID |
| `dist/store-data.js` | データ層: 定数（region／stations／labels）、検証、採番、JSON 変換、Google マップリンク生成、同座標グループ化。DOM に触れない。Node からも `module.exports` で読み込める | なし（単独でテスト可能） |
| `dist/app.js` | 検索画面: 状態管理（type／mode／query／selected）、正規化（NFKC・ひらがな化）＋駅名エイリアスによる絞り込み、一覧・ピン・詳細の描画、実地図の遅延読み込みとフォールバック判定、初期データ読み込み（`boot()`）、`setRows()` の公開 | `StoreData`、DOM、（任意）MapLibre |
| `dist/cms.js` | 管理画面: ハッシュルーティング（`#manage` の表示切替）、CRUD、localStorage 保存、JSON 入出力 | `StoreData`、app.js が公開する `rows`／`setRows()`／`storeReady` 等のグローバル |
| `build-data.mjs` | CSV → JSON 生成と CSV 側検証（リポジトリ直下、配信対象外） | Node、 `dist/stores.csv` |
| `test-store.js` | データ層の単体確認（16 項目） | Node、`dist/store-data.js`、`dist/stores.json` |
| `test-browser.cjs` | 画面のブラウザ確認（Playwright＋Chromium、外部地図は読み込まない） | Playwright |

結合点は意図的に 3 つだけに絞られている: (1) `StoreData` の公開 API、(2) app.js が公開する `rows`／`setRows()`／`storeReady`、(3) localStorage キーと JSON 形式（version 1）。変更時はこの 3 点の互換を先に確認する。

## 5. ディレクトリ構成の判断と今後の分割案

現行は「配信物＝ソース」のフラット構成で、ファイル数・規模に対して妥当と判断し、この文書の PR ではファイル移動は行わない。移動すると相対パス（`stores.json` の fetch、`stores.csv` リンク、テストの相対 require）が一斉に変わり、ビルド無し構成では壊れやすさだけが増えるためである。

将来、以下のいずれかに当てはまったら、段階案に沿って分割する:

- 店舗データの項目追加や、画面が 3 つ以上に増える
- JS が肥大化し、検索と管理の変更が相互に影響し始める

段階案（各段階を独立した PR にし、動作確認を通してから次へ進む）:

1. データを `dist/data/`（stores.csv／stores.json）へ分離し、参照パスとテストを追随させる。
2. スタイルを画面別（検索／管理）に分割する。読み込み順とカスケードの変化をブラウザテストで確認する。
3. JS を ES Modules 化する場合は、配信方法（静的配信のままか、簡易バンドル導入か）を先に決める。`StoreData` の Node 互換（`module.exports`）をどう維持するかもこの段階で決める。

## 6. 動作確認の基準

- `node test-store.js` が 16 項目を通ること。
- ローカルサーバー（README の手順）で検索画面と管理画面が開き、検索・絞り込み・ピン選択・追加／編集／削除・JSON 入出力ができること。
- 地図 CDN／タイルに接続できない環境でも、略図フォールバックで検索と選択が使えること。
- 外部地図リンクは座標ベース（店名検索ではない）で、架空店舗である注意書きが詳細に残っていること。
